StockFlow — Product Requirements Document

Phase 2: Core Application, Data Model & Role-Based Access

1. Background

StockFlow's marketing site and admin foundation are built. This PRD scopes the next phase: turning StockFlow from a marketing site with an admin CMS into the actual inventory management product it advertises — the dashboard, products, warehouses, suppliers, purchases, and sales screens shown in the landing page's own product preview.

3. Goal of Phase 2

Ship the Manager Console — the actual day-to-day application a business owner or manager uses to run their inventory operation, matching the sidebar shown in the product preview: Dashboard, Products, Inventory, Warehouses, Suppliers, Purchases, Sales, Reports, Settings.

Phase 2 is split into three parts, in build order:

  1. Data model — define every entity the core app needs and migrate the database once, rather than piecemeal per screen.
  2. Manager Console features — the actual CRUD/workflow screens built on that data model.
  3. Roles & permissions — restrict who can do what, now that there's more than one kind of user and more than one kind of action to protect.

4. Part A — Data Model

4.1 New entities

Entity Purpose Key fields
CategoryGroups products for organization and reportingName, Description
ProductA sellable/stockable itemName, SKU, CategoryId, PreferredSupplierId, UnitPrice, ReorderLevel, IsActive
WarehouseA physical stock locationName, Location, IsActive
InventoryItemStock quantity of one product at one warehouse (junction table)ProductId, WarehouseId, QuantityOnHand
SupplierA vendor products are purchased fromName, ContactEmail, ContactPhone, Address, IsActive
PurchaseOrderAn order placed to a supplierSupplierId, Status, OrderDate, ExpectedDate, CreatedByUserId, TotalAmount
PurchaseOrderItemLine item on a purchase orderPurchaseOrderId, ProductId, Quantity, UnitCost
CustomerWho a sale is made toName, Email, Phone
SalesOrderAn order placed by a customerCustomerId, WarehouseId, Status, OrderDate, CreatedByUserId, TotalAmount
SalesOrderItemLine item on a sales orderSalesOrderId, ProductId, Quantity, UnitPrice
StockMovementAudit log of every stock changeProductId, WarehouseId, ChangeQuantity, Reason (Purchase/Sale/Adjustment), ReferenceId, CreatedAtUtc

Relationships:

  • Product → Category (many-to-one)
  • Product → Supplier (many-to-one, optional — the preferred supplier for reordering; a purchase order can still be placed with a different supplier when needed)
  • Product → InventoryItem → Warehouse (many-to-many via InventoryItem)
  • PurchaseOrder → Supplier (many-to-one), → PurchaseOrderItem (one-to-many) → Product
  • SalesOrder → Customer (many-to-one), → SalesOrderItem (one-to-many) → Product
  • StockMovement is the single source of truth for stock history — both receiving a purchase order and completing a sales order write a row here, rather than only mutating InventoryItem.QuantityOnHand directly. This is what makes "Recent Activities" and "Low Stock Alert" on the dashboard buildable as simple queries instead of separate hand-maintained state.
📊 Dashboard metrics are not their own entity — Total Products, Total Orders, Total Revenue, Sales Overview, Inventory by Category are all computed on read from the tables above, not stored redundantly.

Soft-delete convention

Product, Supplier, and Warehouse are never hard-deleted once they have order history — "Delete" in the UI sets IsActive = false instead of removing the row. Inactive records:

  • Are excluded from dropdowns/selectors when creating a new purchase order, sales order, or product.
  • Still render correctly on historical orders that already reference them (an old sales order still shows the discontinued product's name).
  • Can be "restored" (IsActive = true) from a dedicated view if needed later — not required for MVP, but the flag makes it trivial to add.

A record with no order history at all (e.g. a product created by mistake and never ordered) can still be hard-deleted safely, since nothing else references it — worth a quick existence check in the delete endpoint (if referenced anywhere → soft-delete; if not → hard-delete) rather than always soft-deleting everything.

4.2 Migration plan

  • Add all entities above to Domain/Entities/, following the same onion structure as Plan/Contact.
  • Configure relationships in AppDbContext.OnModelCreating (foreign keys, cascade rules — e.g. deleting a Product should probably be blocked or soft-deleted if it has order history, not cascade-deleted).
  • One migration for the full schema: dotnet ef migrations add CoreDomainModel, then dotnet ef database update.
  • Seed reference data that screens need immediately to be usable: a couple of Category rows, one default Warehouse, so Products/Inventory aren't empty on first login.
❓ Open question to confirm before migrating: should Product support multiple suppliers, or one preferred supplier per product? The table above assumes suppliers are only linked through PurchaseOrder, not directly on Product — confirm this matches intent before locking the schema.

5. Part B — Manager Console Features

Build order follows the dependency chain — later screens need data from earlier ones to be meaningful:

Order Module Core actions
1Categories & WarehousesCRUD — simplest, needed before Products can be created
2ProductsCRUD, assign category, set reorder level
3InventoryView stock per product per warehouse, manual stock adjustment (writes a StockMovement with Reason = Adjustment)
4SuppliersCRUD
5PurchasesCreate purchase order → mark received (writes StockMovement with Reason = Purchase, increments InventoryItem)
6SalesCreate sales order → mark fulfilled (writes StockMovement with Reason = Sale, decrements InventoryItem)
7DashboardAggregate queries over the above: totals, low-stock list, recent activity feed, inventory-by-category breakdown

Each module follows the same shape already established for Plans: Domain entity → DTOs → repository/service interfaces → service → controller → admin-style CRUD page → JS module (service/validation/page files).

6. Part C — Roles & Permissions

6.1 Why now, not earlier

Phase 1 only needed "authenticated or not" — one admin, one set of permissions. Phase 2 introduces real operational differences: an owner shouldn't want every staff member able to delete purchase orders or manage other users' accounts.

6.2 Proposed roles (MVP scope)

Role Can do
OwnerEverything, including Team Management and Settings. Exactly one per business in MVP — the seeded admin account.
ManagerFull access to Products, Inventory, Warehouses, Suppliers, Purchases, Sales, Reports. Cannot manage Team or Settings.
StaffRead access to Inventory and Products; can create Sales Orders. Cannot delete anything, cannot access Purchases, Suppliers, Reports, Team, or Settings.

This is intentionally simple (3 fixed roles, not a granular permission-editor) to ship something usable quickly. A fine-grained, admin-configurable permission system is a reasonable Phase 3 idea, not part of this scope.

6.3 Implementation approach

  • User.Role already exists as a string — formalize it as an enum (Owner, Manager, Staff) at the database/DTO level.
  • Enforce with ASP.NET Core's built-in [Authorize(Roles = "Owner,Manager")] on controllers/actions — no custom permission engine needed for 3 fixed roles.
  • The JWT already carries a role claim (set up in Phase 1's TokenService) — this phase mostly wires existing claims into new [Authorize] attributes, it doesn't require new auth infrastructure.
  • Frontend: hide nav links/buttons the current user's role can't use (convenience, not security — the backend [Authorize] check is what actually protects anything). A small authState.js helper (hasRole(role)) can drive this.

7. Suggested Milestones

  • Milestone 1 — Data model migrated, seed data in place, Categories + Warehouses + Products CRUD live.
  • Milestone 2 — Inventory view + manual adjustments working; Suppliers CRUD live.
  • Milestone 3 — Purchases and Sales workflows live, StockMovement correctly updates InventoryItem on both.
  • Milestone 4 — Dashboard built entirely from real data (no more static mockup numbers).
  • Milestone 5 — Roles enforced across every controller; Team Management screen live.
  • Milestone 6 — Reports + Settings; polish pass.

8. Out of Scope for Phase 2

  • Multi-tenancy (multiple separate businesses using one deployment)
  • Granular, admin-configurable permissions beyond the 3 fixed roles
  • Barcode scanning / hardware integration
  • Automated reordering from suppliers when stock is low (flagging low stock is in scope; auto-ordering is not)
